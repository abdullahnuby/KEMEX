# مراجعة KEMEX v0.23.1 → v0.24.0

المنهج: فتحت المشروع، شغّلت `npm install` و`typecheck` و`build` (نجحوا)، وبعدين شغّلت migrations 001–007 والـ seeds على Postgres حقيقي (PGlite/WASM) وجرّبت الصلاحيات بأدوار مختلفة (JWT claim → `auth.uid()`). كل بند تحت اتجرّب فعليًا إلا لو مكتوب غير كده.

## اللي كان شغّال كويس (ما اتغيّرش)
- معمارية React + TS + Vite نظيفة، وطبقة `repository` تبدّل بين Demo وSupabase.
- دوال `private.*` كـ `security definer` مع `search_path` مثبّت، وGRANTs صريحة، وفهارس، وRLS مفعّلة على كل الجداول.
- سجل تدقيق بدون UPDATE/DELETE، وسياسة `audit_insert` بتربط الصف بـ `auth.uid()`.
- مفيش أسرار في الواجهة (publishable key فقط).

## اللي اتضاف
- `supabase/migrations/008_security_and_integrity.sql`: مصفوفة صلاحيات واحدة (قراءة/كتابة) في `private.module_permissions`، جدول `workflow_transitions` (نفس انتقالات `modules.ts`)، مشغّلات تدقيق/اعتماد/ترقيم، وحماية `profiles`. قابلة لإعادة التشغيل.
- `tests/db/rls.test.mjs` (`npm run test:db`): 11 اختبارًا بيشغّلوا كل الـ migrations والـ seeds ويجرّبوا الأدوار. متضاف للـ CI.

## اللي متغيّر في الواجهة (ملفات صغيرة)
`repository.ts` (pageAll، onConflict، لا كتابة تدقيق/اعتماد من العميل، قفل Demo) • `App.tsx` (بوابات صلاحية للصيانة/الوقود/المشروعات/الأصول) • `AssetsPage.tsx` • `LoginPage.tsx`.

## سلوك جديد لازم تعرفه
- التغييرات اللي بتتم من SQL Editor أو service role **مش بتتسجّل** في `audit_log` ولا بتمرّ على حارس الاعتماد (`auth.uid()` فاضي). ده مقصود عشان الـ seed والصيانة.
- الأدمن يتخطّى حارس الانتقالات (للتصحيح)، لكن عملياته بتتسجّل.
- الرقم اللي يتعرض في نموذج "طلب جديد" مؤقت؛ الرقم النهائي بيرجع من الخادم بعد الحفظ.

## اللي لسه مفتوح (مرتب بالأولوية)
1. **المنطق متعدد الخطوات في المتصفح**: اعتماد تشغيل ← تحديث عداد الأصل، وإنهاء تخصيص ← تحرير الأصل ← إغلاق الطلب. كل خطوة كتابة منفصلة. لو انقطع النت بعد الأولى البيانات تتناقض. الحل: RPC/مشغّل واحد transactional.
2. **`operations`/`assignments` نوعية موجودة ومهملة**: الواجهة بتخزن التشغيل والطلبات والتخصيصات كـ JSON في `tfms_module_records` (بلا FK ولا أنواع ولا SQL aggregation). التكاليف والوقود بتتحسب كلها في المتصفح. الأنسب ترحيل `operations` ثم `requests`/`assignments` للجداول النوعية، وبعدها views/RPC للتكاليف.
3. **تعارض التزامن**: مفيش optimistic concurrency (إصدار/`updated_at` في الشرط). مستخدمين يعدّلوا نفس السجل = آخر كاتب يفوز.
4. **`attachments` و`user_notifications`**: الجداول موجودة بدون bucket ولا سياسات storage ولا منشئ إشعارات. الميزة مش شغّالة بعد.
5. صفحات `plans` و`inventory` بتعرض أزرار الحفظ لكل من يشوفها (القاعدة بترفض، الواجهة بتعرض الخطأ).
6. حزمة JS واحدة 634KB (154KB gzip): `React.lazy` لكل صفحة يقلّلها.
7. الاختبارات بتغطي القاعدة فقط. مفيش اختبارات لمحرك التكاليف/الاستحقاقات (منطق مالي محسوب في المتصفح).
8. Realtime: كل مستخدم بيشوف بيانات وقت التحميل فقط.

## حدود الاختبار
اتجرّبت على PGlite (Postgres 18 WASM) مع محاكاة `auth.uid()`. لم أختبر على مشروع Supabase حي ولا في متصفح. سلوك PostgREST/`supabase-js` (الـ upsert وحدود الـ 1000 صف) مستنتج من السلوك الموثّق ومن الـ SQL المكافئ.
